# 实验后处理优化

## 目标

实验完成后，最慢的环节应当只执行一次；人类判断仍然显式保留，但不能让一个
`status`、`evidence_role` 或 provenance 字段错误触发数 GB 原始日志的重新扫描。
统一入口是：

```bash
export PYTHONUTF8=1
python ./tools/postprocess_experiment.py closeout \
  --experiment ./HP_V8/exp_YYYYMMDD_SLUG \
  --archive ../hybridpatch_private_archives/exp_YYYYMMDD_SLUG_raw.tgz \
  --confirm-stopped
```

该命令零 API、可重复运行，并按当前状态继续：

```text
strict inspection（按输入快指纹缓存）
  → prepare（已有且输入未变则复用）
  → WAITING_FOR_REVIEW（人工和独立审阅边界）
  → review/catalog/record validate-only（不读 raw body）
  → 权威凭据/tree 扫描与原生 tgz 并行生成 seal
  → finalize 复用 seal，不再扫描 raw tree
```

第一次运行通常停在 `WAITING_FOR_REVIEW`。完成
`analysis/record_review.yaml` 后原命令重跑；strict inspection 与 prepare 命中缓存，
先做完整轻量契约检查，再进入归档和 finalize。

## 为什么此前耗时长

由近到远，问题不是单一脚本慢，而是流程缺少阶段契约：

1. `mixed_confirmation100` 后处理里，strict inspector 对同一冻结输入运行了两次；
   credential scan、raw tree hash 和压缩分别读取约 2.5 GB 目录。
2. finalize 的 raw tree hash 位于 builder 的 schema/vocabulary/provenance 检查之前。
   因而 `evidence_role`、status、dual-commit recovery、legacy fingerprint 等轻量错误，
   每次都先付出一次数分钟扫描成本。
3. 全局 catalog digest 会刷新所有 generated records。私有 source-only record 若不应发布，
   过去需要手工快照、移开 orphan record、运行 validator、打包，再恢复。
4. 2026-07-17 和 2026-07-18 的 experiment log 已出现“generated record 私有保存、
   恢复旧 generated state”的相同模式，说明这不是单次偶发操作，而是应当编码的流程。

## 已封装的阶段

### 1. 快速状态

```bash
python ./tools/postprocess_experiment.py status \
  --experiment ./HP_V8/exp_YYYYMMDD_SLUG
```

只检查控制文件和 result/task-plan digest，不读取完整 raw response body。输出
`prepared_current`、`review_pending`、strict inspection 是否存在以及 process stage。

### 2. strict inspection 缓存

```bash
python ./tools/postprocess_experiment.py inspect \
  --experiment ./HP_V8/exp_YYYYMMDD_SLUG
```

缓存键是 analysis 以外文件的 path/size/mtime-ns 快指纹。它不是研究证据哈希；用途仅是
判断昂贵 inspection 是否需要重跑。正式证据仍由 inspector 输出、result digest 和最终
SHA-256 承担。任何源文件变化都会使缓存失效；`--force` 可明确重跑。

正式 `evaluator_incomplete` 由 runner 直接写入 sample outcome、run metadata 和
`anchorpatch.evaluator_incomplete/2` sidecar。strict inspector 会复核失败步骤没有结果行、
checkpoint 仍是完整前缀、没有补 0；`collect_facts` 和 complete-pair scope 会保留每个缺失
样本的具体 outcome。这样后处理不再依赖人工从 console log 猜测 evaluator 故障，也不会把
它误标成 infrastructure failure。历史 `/1` sidecar 仍按原 source-log SHA 语义读取。

### 3. 先验 review/record 契约检查

```bash
python ./tools/process_experiment.py review-check \
  --experiment ./HP_V8/exp_YYYYMMDD_SLUG
```

该命令在仓库同盘临时目录生成 record，覆盖 scope、catalog vocabulary、provenance、
source report 和 record builder 契约，然后丢弃临时输出。它不计算 raw tree hash、不改
catalog、records 或 indexes。finalize 内部也会先执行同一 validate-only 门禁，所以直接
调用旧 finalize 入口仍然先轻后重。

### 4. 并行私有归档 seal

```bash
python ./tools/postprocess_experiment.py seal \
  --experiment ./HP_V8/exp_YYYYMMDD_SLUG \
  --archive ../hybridpatch_private_archives/exp_YYYYMMDD_SLUG_raw.tgz
```

seal 同时启动两条只读任务，以墙钟时间而不是理论读盘次数为优先：

- Git Bash 原生 `tar+gzip` 压缩；
- 现有 record builder 的每文件 SHA-256、`sha256-tree-v1`、本机 `.env*` 精确凭据
  匹配及 Authorization/Cookie/API-key/PEM 保守 marker 统计。

两条任务会各自只读源目录，但并行执行；finalize 复用 seal，不再进行第三次 raw-tree
扫描。首次耗时接近“权威扫描”和“原生压缩”中较慢的一项，重复执行仅做元数据快指纹。

Key 值不会写入日志、scan、seal 或 archive。精确 Key 命中或本机没有可用 Key 值时，
归档不会发布。seal 用 path/size/mtime-ns 检查源目录未变；相同输入重跑直接命中缓存，
源改变则拒绝覆盖，除非明确指定新文件名或 `--force`。

finalize 可复用 seal：

```bash
python ./tools/process_experiment.py finalize \
  --experiment ./HP_V8/exp_YYYYMMDD_SLUG \
  --sealed-manifest ../hybridpatch_private_archives/exp_YYYYMMDD_SLUG_raw.tgz.seal.json
```

### 5. 私有 source-only record

不应修改已发布 catalog/records 时，使用：

```bash
python ./tools/postprocess_experiment.py closeout \
  --experiment ./HP_V8/exp_YYYYMMDD_SLUG \
  --archive ../hybridpatch_private_archives/exp_YYYYMMDD_SLUG_raw.tgz \
  --private-record-bundle ../hybridpatch_private_archives/exp_YYYYMMDD_SLUG_record.tgz \
  --confirm-stopped
```

工具会在验证通过的 generated state 中打包新 record、prospective catalog 和 indexes，
随后恢复进入命令前的 catalog/index/records，包括既有本地 orphan record。无需手工移动
目录，也不会把私有 record 混入已发布索引。`process_state.json` 标记
`finalized_private` 并保存 bundle SHA-256。

## 仍然不能自动化的内容

- canonical scope、排除理由、claim role、known exception 和 paper reporting；
- 正式实验规定的独立只读审阅；
- marker 是否为任务文档字面量的语义判断；
- 对不完整 campaign 是否允许 complete-pair supporting view 的研究边界。

脚本只消除重复 I/O 和机械返工，不用自动推断替代这些判断。首次 strict inspection、
verifier/analyzer 和压缩仍是实际工作；优化目标是让它们各运行一次，而不是隐藏成本。

## V8 实际归档零 API 基准

2026-07-20 使用已完成的
`HP_V8/exp_20260719_hybridv8_transportv4_mixed_confirmation100` 做了只读实测。测试时源树
为 37,771 个文件、2,548,894,527 字节；其中一个文件是独立 strict-cache sidecar，测试后
已删除。原 strict inspection 和 private scan 文件在测试前备份，测试后逐字节恢复；没有
调用 API，也没有改写任务结果、checkpoint 或 raw request/response。

| 操作 | 墙钟时间 | 说明 |
|---|---:|---|
| 历史首次 strict inspection | 约 278 秒 | 此前实际运行观察值；不是本次重跑 |
| 采用已有、已被 finalized 分析引用的 strict 证据 | 8.0 秒 | 只创建独立 cache sidecar，不改 strict 证据 |
| strict inspection cache hit | 7.6 秒 | 快指纹核验 |
| 单独权威 credential/tree scan | 284.4 秒 | 37,771 个文件，精确本机凭据命中 0 |
| Python 串行读流归档原型 | 465.4 秒 | 性能不合格，已弃用 |
| 权威扫描与 Git Bash 原生压缩并行 seal | 297.3 秒 | tree SHA-256 与单独权威扫描一致 |
| seal cache hit | 7.7 秒 | 校验快指纹和既有 archive/seal |
| `review-check` | 3.9 秒 | 98 个 canonical sample，不扫描 raw body |

并行 seal 的 tree SHA-256 为
`a6a3a3790b16844d486e6b1297a9942d4b1eaa9a2bdb57aea15cd915f0d0a520`，与单独权威
扫描相同；生成的 tgz 为 470,551,931 字节。并行版把归档墙钟时间压到接近权威扫描本身，
并让后续 finalize 直接复用 seal。它没有消除首次 2.5 GB 权威扫描成本；若还需缩短首次
运行，下一步应单独优化凭据匹配和 tree hashing，而不是跳过证据检查。
