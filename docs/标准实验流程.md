# 标准实验流程

本文是 HybridPatch 新实验的端到端操作说明。根目录 `AGENTS.md` 规定必须执行的步骤；本文展开每一步要创建什么、更新什么、由谁检查，以及何时允许进入下一阶段。

适用范围：

- 新 HP_V8+ 方法实验以及后续迭代实验；
- baseline 或 transport 的新付费实验；
- 会影响方法设计、正式结论或后续迭代的诊断实验；
- 准备用于论文、GitHub 外部模型审阅或重新评分的实验。

冻结的 HP_V3–HP_V7 不回补执行本流程；它们只保留已经生成的 provenance records。

## 1. 总流程

```text
确定问题与实验编号
  → 创建并审阅实验计划
  → 生成零 API receipt（回归 / manifest / evaluator）
  → 独立完成 Key probe 与最终命令复核
  → 固定代码与运行身份
  → 运行、监控、断点续跑
  → 停止全部 worker
  → prepare
  → 独立结果审计与失败分析
  → 主 Agent 完成 record_review.yaml 和研究文档
  → finalize
  → 私有原始日志归档
  → records 与 GitHub 干净 clone 校验
```

正式主实验不得跳过其中任一阶段。付费 smoke 可以缩短分析深度，但不能省略实验编号、计划、preflight、运行身份、worker 停止确认、结果完整性检查和日志保留状态。

## 2. 实验前：创建和更新的内容

### 2.1 创建实验计划

从 [`experiment_plans/TEMPLATE.md`](./experiment_plans/TEMPLATE.md) 复制为：

```text
docs/experiment_plans/<experiment_id>.md
```

计划是实验开始前的事实源，必须回答：

1. 为什么现在做这次实验？
2. 迭代思路来自哪里？如果来自外部模型，它被转写成了什么可证伪假设？
3. 相对上一版本或对照，唯一计划变化是什么？
4. 代码、配置、模型、API、transport、prompt、protocol 和 executor 分别是哪一版？
5. 使用什么数据划分、样本编号、seed 和 task plan？
6. 完整运行命令、并发、预算、停止条件是什么？
7. 主指标、辅助指标、严重失败定义和预注册排除是什么？
8. 正面、负面和不确定结果分别会触发什么决策？
9. 原始请求、模型响应和底层传输日志分别保存到哪一级？

计划中的设计内容在首次正式 API 调用后冻结。实际偏差、事故和临时处置写入 `docs/active_log.md`、原始运行 metadata 和实验后的 review，不回写计划来伪装预注册。

### 2.2 更新实验前文档

| 文件 | 什么时候必须更新 | 内容 |
|---|---|---|
| `docs/active_log.md` | 每次 API 实验 | `Before Experiment`：计划链接、目标、样本、命令、成功信号、停止条件和 guardrails |
| `HP_Vx/VERSION.md` | 新建方法版本或版本方向改变 | 五问摘要、协议/代码来源、计划验证和下一轮问题 |
| `data/CONTAMINATION_REGISTRY.json` | 首次暴露新的 val/test/reserve 样本 | 样本、用途、时间和污染边界 |
| `transport/API_ITERATION_LOG.md` | transport revision、重试或完整性政策改变 | 变更、验证、兼容边界和允许进入 HP 的条件 |
| `docs/experiment_plans/<id>.md` | 每次新 API 实验 | 完整预实验计划 |

### 2.3 实验计划审阅子代理

正式主实验和支持性付费实验开跑前，由主 Agent 创建一个新上下文、只读的“实验计划审阅”子代理。其输出固定为：

```text
verdict: GO | GO WITH FIXES | NO-GO
observed facts:
confounds and contamination:
missing reproducibility fields:
metric and exclusion risks:
required fixes:
evidence locations:
```

检查重点：

- 研究问题能否由本实验回答；
- 是否混入多个无法归因的改动；
- 方法与对照是否使用同一任务序列和适用的 transport 政策；
- 样本是否已经曝光，是否需要降级 claim；
- 指标、严重失败、缺失值和排除是否在看结果前定义；
- command、seed、commit、tree state、配置和预算是否可追踪；
- 失败、无优势或统计不确定时是否仍有预先定义的决策。

子代理不直接修改计划。主 Agent 根据证据修改计划，并记录所有必须修复项已经闭合。

### 2.4 开跑门

先从仓库根运行统一零 API 入口：

```bash
export PYTHONUTF8=1
python ./tools/preflight_experiment.py \
  --experiment ./HP_V8/exp_YYYYMMDD_SLUG \
  --plan ./docs/experiment_plans/exp_YYYYMMDD_SLUG.md \
  --evaluator-jobs 8 \
  -- <已审阅的 paired_campaign_dispatch.py 参数>
```

`--` 后使用正式 dispatcher 参数，但不传 `--out_dir` 和 `--dry_run`；入口会自动注入。
它顺序完成版本零 API 回归、本次 dispatcher dry-run、manifest 样本的并行 runtime
evaluator 检查，并写入
`HP_V8/exp_YYYYMMDD_SLUG/preflight/preflight_receipt.json`。它不会运行 Key probe，
不会启动正式 worker。详细缓存和失效语义见
[`实验前处理优化.md`](./实验前处理优化.md)。

成功的零 API 回归可按 HP 源码和 Python runtime 指纹复用；成功的 evaluator 结果还要求
对应样本内容指纹一致。失败结果不复用，代码、runtime 或样本变化时只重跑失效部分。
dispatcher dry-run 绑定本次命令和 manifest，始终执行。随后独立运行既有 Key 最小探针，
再复核正式启动命令。

开跑前至少确认：

```text
计划文件存在且字段完整
Before Experiment 已写入 active_log
目标 HP 版本为 active 且不是冻结版本
零 API receipt 为 PASS，计划与 manifest SHA-256 已保存
数据、task plan 和 manifest 样本 runtime evaluator preflight 通过
Key 最小探针通过
最终命令、out_dir 和预算复核完成
runner 能记录 run_git_commit / git_tree_state / started_at / finished_at
没有凭据复制进实验目录
实验计划审阅结论为 GO，或 GO WITH FIXES 且修复已完成
```

任何一项不满足都不得正式开跑。

断点续跑不需要在输入指纹未变时重复执行昂贵回归或 evaluator；统一入口会复用成功
结果，但仍以实际 resume 参数重跑 dispatcher dry-run。Key probe 保持独立，不能由历史
零 API receipt 替代。

## 3. 运行中

- 运行只写入所属的新 `exp_*`，不得与其他调度器共享同一 `out_dir`。
- 每个 round trip 原子保留结果行、checkpoint、调用定位和必要 ledger。
- 断点续跑只补未提交项；不得删除、覆盖或重掷已提交结果。
- 运行中不得修改方法语义、prompt、transport revision、数据范围、seed、task plan、比较政策或 evaluator。
- 必须记录异常发生在 API 调用前还是调用后；检查 `api_calls.jsonl`、`api_raw`、response journal 和 checkpoint 后再判断是否产生费用或是否可重放。
- 确定性本地错误先修根因并建立新实验编号；不得通过轮换 Key 重试。

大规模 paired campaign 使用 `per_key_work_conserving_v1` 调度。每个 Key 的并发上限仍由
`--slots_per_key` 固定；某个 worker 结束后，dispatcher 立即从同一 Key 的稳定 FIFO 队列
补位，不等待整批 worker 清空。不同 Key 的空闲槽位不能互借，任何时刻均不得超过每 Key
上限。`dispatch_manifest.json` 保存每 Key 队列、最大 worker 数和 queued worker 数；
`dispatch_log.jsonl` 保存每次 refill、槽位释放和剩余队列数量。

异常隔离遵循以下固定边界：

- transport/provider 预算耗尽：仅在既有四方证据链通过时记为
  `infrastructure_incomplete`，允许按授权规则恢复；
- `domain.evaluate_context()` 抛异常：仅在 sample outcome、run metadata、
  `evaluator_incomplete_samples.jsonl` 和实际 checkpoint 一致，且失败步骤没有结果行、没有
  0 分插补时记为 `evaluator_incomplete`。该样本在本 campaign 内终止，其他 worker 和该
  Key 后续队列继续；resume 跳过它；
- preservation、Git/task-plan 漂移、重复或半提交结果、无法映射的 API ledger、普通 runner/
  本地代码异常、evaluator 证据不完整：仍立即停止整个 campaign。

因此，campaign 可以以 incomplete 状态收尾。正式 endpoint 对未完成样本保持 null；后处理
只生成明确标注的 complete-pair 派生视图，不把缺失样本写成 0，也不声称达到预注册固定 n。

如果必须改变计划，停止当前实验并将其标记为 `incomplete` 或 `failed_informative`。新设计使用新实验编号和新计划，不在原目录继续混跑。

## 4. 实验后：分析、报告和日志处理

### 4.1 冻结 raw 输出并运行 prepare

确认所有 worker 停止后，从仓库根运行：

```bash
export PYTHONUTF8=1
python ./tools/process_experiment.py prepare \
  --experiment ./HP_V8/exp_YYYYMMDD_SLUG \
  --confirm-stopped
```

对新的 paired campaign，推荐改用可恢复的统一入口；它会缓存 strict inspection、
复用有效 prepare，并在需要人工审阅时明确停下：

```bash
python ./tools/postprocess_experiment.py closeout \
  --experiment ./HP_V8/exp_YYYYMMDD_SLUG \
  --archive ../hybridpatch_private_archives/exp_YYYYMMDD_SLUG_raw.tgz \
  --confirm-stopped
```

同一命令在审阅前后重复运行不会重复昂贵阶段。完整缓存、seal、私有 source-only record
用法见 [`实验后处理优化.md`](./实验后处理优化.md)。

`prepare` 运行版本本地 verifier/analyzer，并创建：

```text
analysis/verification.log
analysis/analysis.log
analysis/comparison.md
analysis/experiment_results.csv
analysis/derived_facts.json
analysis/process_state.json
analysis/record_review.yaml
```

`prepare` 同时要求 `docs/experiment_plans/<experiment_id>.md` 已存在，检查其中的
实验编号和 owner，并记录计划文件 SHA-256。计划在 prepare 后发生变化时，
finalize 会拒绝继续。

机械事实只进入 `derived_facts.json`。canonical scope、排除理由、claim role、source reports、known exceptions 和 paper reporting 必须由主 Agent 在独立审阅后写入 `record_review.yaml`。

`record_review.yaml` 还必须填写 `review_provenance`：主审阅者、ISO 时间、审阅
方式、独立子代理的角色/审阅者/verdict/摘要。未创建独立审阅的付费 smoke 必须填写
明确的 exception reason；正式主实验不得使用该例外替代规定的独立审阅。

### 4.2 固定的实验后子代理

正式主实验默认创建三个新上下文、只读子代理；可并行执行：

| 角色 | 必查内容 | 交付 |
|---|---|---|
| 结果完整性审计 | 计划网格、行数、checkpoint、metadata、fingerprint、verification、缺失值、排除、敏感信息、raw manifest | `PASS/FAIL`、承重事实、阻塞项、建议的 scope/exception |
| 结果与失败分析 | 汇总指标、逐样本差异、casebook、严重失败、route/status、token/耗时、代码映射 | 观察、机制解释、可证伪的下一改动、典型案例定位 |
| 结论边界审阅 | 统计不确定性、混杂、post-hoc 处理、claim eligibility、paper reporting | 允许声明、禁止声明、必须披露、需要补做的实验 |

支持性或诊断实验可以合并“结果与失败分析”和“结论边界审阅”；结果完整性审计不能省略。付费 smoke 至少需要一个独立结果审阅，或由主 Agent在 `record_review.yaml` 中说明为何不另建子代理。

子代理只读；主 Agent 独占以下文件的写入权：

```text
analysis/record_review.yaml
tools/experiment_records_catalog.json
docs/FINDINGS.md
docs/RESEARCH_JOURNAL.md
docs/active_log.md
HP_Vx/VERSION.md
```

### 4.3 实验后文档更新矩阵

| 文件/目录 | 更新规则 |
|---|---|
| `docs/active_log.md` | 每次 API 实验追加 `After Experiment`，记录完成度、verification、主要结果、异常、偏离计划和下一决定 |
| `analysis/record_review.yaml` | 每次 V8+ record 必须人工审核；加入计划文件作为 `pre_registered_experiment_plan` source report |
| `docs/RESEARCH_JOURNAL.md` | 每个重要 campaign 按其模板追加；保留配置、结果、归因和混杂 |
| `docs/FINDINGS.md` | 出现新机制、新 bug、新失败类型、反例或设计决策时追加；只重复已有现象时引用旧条目 |
| `HP_Vx/VERSION.md` | 本版效果、新问题或下一轮发生变化时更新；冻结前必须与 records 一致 |
| `transport/API_ITERATION_LOG.md` | transport 诊断或政策变化时更新 |
| `docs/项目结构与迭代史.md` | 版本收官、canonical 结果或下一迭代状态变化时更新 |
| `docs/AI_REVIEW_GUIDE.md` | 外部模型的 current result boundary、阅读顺序或下一轮审阅目标变化时更新 |
| `records/`、owner `EXPERIMENTS.md`、`docs/EXPERIMENT_INDEX.md` | 只由 finalize/生成器更新，禁止手改 |

“每次实验后检查这些文档”不等于每份都必须增加文字。没有新内容时保持不变，避免制造重复历史；但主 Agent 必须逐项判断适用性。

### 4.4 finalize 与 Git records

审核完成后运行：

```bash
python ./tools/process_experiment.py finalize \
  --experiment ./HP_V8/exp_YYYYMMDD_SLUG
```

finalize 会先在同盘临时目录执行 `--validate-only --skip-tree-hash`，确保 review、catalog、
provenance 和 record-builder 契约全部通过后才读取 raw tree。若已经由统一后处理入口生成
`.seal.json`，使用 `--sealed-manifest` 可复用 seal 中的 tree hash 与 credential scan。

finalize 会生成：

```text
experiment.yaml
report.md
summary.json
samples.csv
casebook.jsonl
failure_stats.json
representative_failures.jsonl
verification.txt
raw_manifest.json
```

其中：

- `report.md` 是 canonical human report；
- `summary.json` 是唯一 canonical machine scope；
- `casebook.jsonl` 是下一轮代码与失败分析入口；
- `raw_manifest.json` 记录 raw 位置、哈希、大小和清理状态。

### 4.5 原始日志三级保存

| 层级 | 保存内容 | 处理 |
|---|---|---|
| 一级 | 配置、summary、逐样本指标、失败统计、代表案例、verification | Git records |
| 二级 | 清理后的请求、模型原始响应、必要执行结果和可重评分材料 | 私有压缩归档或对象存储 |
| 三级 | HTTP header、Cookie、连接、心跳、重复 retry/debug 输出 | 临时保存，取证价值结束后删除 |

二级归档尚未完成时必须写 `not_compressed`、`not_rechecked` 或其他真实状态，不能仅因已有 `raw_manifest.json` 就声称完成了清理或上传。

## 5. 完成标准

实验只有同时满足下列条件才算“已经整理完成”：

```text
原始运行停止且没有继续写入
计划—实际偏差已披露
verification 结果已记录
缺失样本和排除均有明确理由
独立结果审阅已完成
record_review.yaml 已人工审核
应更新的研究文档已判断并处理
finalize 成功生成九件套
本地 validator PASS
records-only validator PASS
原始日志的清理、压缩和保存状态真实可见
Git diff 和敏感信息检查完成
```

若其中任何一项未完成，应将实验描述为“运行结束但尚未完成整理”，不能直接当作可发布的正式证据。
