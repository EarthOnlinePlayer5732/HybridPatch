# 实验前处理优化

## 结论

Key probe 保持为独立的真实 provider 检查。耗时的零 API 阶段统一由一个轻量入口编排：

```bash
export PYTHONUTF8=1
python ./tools/preflight_experiment.py \
  --experiment ./HP_V8/exp_YYYYMMDD_SLUG \
  --plan ./docs/experiment_plans/exp_YYYYMMDD_SLUG.md \
  --evaluator-jobs 8 \
  -- <已审阅的 paired_campaign_dispatch.py 参数>
```

`--` 后复制正式 dispatcher 参数，但不要重复传 `--out_dir` 或 `--dry_run`；统一入口会
自动注入这两个参数。命令只生成本地文件，不发送 provider POST，也不启动正式 worker。

成功后生成：

```text
HP_V8/exp_YYYYMMDD_SLUG/preflight/preflight_receipt.json
```

receipt 固定计划 SHA-256、dispatcher manifest、样本范围、Git 运行身份、回归结果、
evaluator 输入指纹和实际执行/复用数量。它把“哪些检查真实运行过”变成机器可读事实，
避免靠聊天上下文或人工日志回忆。

## 哪些步骤仍然执行

统一入口按固定顺序执行：

1. 三条版本本地零 API 回归：`test_hybrid_executor.py`、`splitters.py`、
   `test_model_openai.py`；
2. 本次正式 dispatcher 命令的 `--dry_run`，生成或核对 task plan 与
   `dispatch_manifest.json`；
3. 仅针对 manifest 样本的 runtime evaluator preflight；
4. 写入零 API receipt，并明确下一步仍需单独 Key probe。

这里没有取消 dry-run，而是把它缩成一个可复用、可审计的开跑门。dispatcher dry-run
本身较轻且绑定本次命令，所以每次执行；昂贵回归和 evaluator 才使用缓存。

## evaluator 加速与缓存边界

`tools/evaluator_runtime_preflight.py` 支持：

```bash
python -B ./tools/evaluator_runtime_preflight.py \
  --samples <sample...> \
  --jobs 8 \
  --output <cache.json> \
  --reuse-output \
  --quiet
```

- `--jobs` 使用有界并发，每个样本仍在独立 Python 子进程中运行；最终报告保持 manifest
  顺序。
- 并行时由父进程统一检查运行前后 `tmp_eval_*`，避免把其他 worker 的短生命周期目录
  误判为泄漏。
- 只有 `runtime_runnable`、API guard 生效、样本树未变化且无临时目录泄漏的结果可复用。
- Python runtime、HP 源码或该样本内容指纹变化时，相关缓存失效；失败、超时和不支持
  结果每次重新执行，绝不缓存成通过。
- cache 位于被 Git 忽略的 `.cache/hybridpatch/preflight/`；正式实验目录只保存 receipt。

2026-07-21 在 HP_V8 上用 10 个真实样本做零 API 对照，三次均为 10/10
`runtime_runnable`：

| 模式 | 墙钟时间 | 执行/复用 |
|---|---:|---:|
| 串行 `--jobs 1` | 31.317 秒 | 10 / 0 |
| 并行 `--jobs 8` | 7.703 秒 | 10 / 0 |
| 指纹一致的缓存命中 | 0.266 秒 | 0 / 10 |

这批样本上的并行墙钟约为串行的 24.6%，即约 4.1 倍加速。该数字只是本机流程基准，
不是方法效果实验；不同 evaluator 的 CPU、I/O 和进程启动成本会改变加速比。

## 234-sample 正式调度入口

`paired_campaign_dispatch.py --campaign_role full234` 自动读取并冻结
`samples_delegate52` 中按名称排序的 234 个样本，不接受手工样本列表。正式配置固定为
10 RT、seed 42、13 个物理唯一 Key、每 Key 4 个 paired workers；manifest 同时保存 234 个
`sample.json` 的集合摘要和完整 task-plan 摘要。开跑前仍必须经过本文件开头的统一 preflight
和独立 Key probe。

full234 与 confirmation 使用 `per_key_work_conserving_v1`：每个 Key 有自己的稳定 FIFO
队列，初始最多启动 4 个 worker；任一 worker 结束后立刻补入该 Key 的下一项，不等待所谓
“第一波”其余 worker。13 Key 的总并发上限为 52，但该数字是上限而不是波次大小。
每个 Key 的初始四个 worker 仍保持两个 HP-first、两个 FullRewrite-first。

dispatcher 参数形态为：

```bash
--campaign_role full234 --num_round_trips 10 --seed 42 \
  --slots_per_key 4 --key_labels KEY_01 KEY_02 ... KEY_13 \
  --notes <experiment-note>
```

不要传 `--samples`；完整样本范围由 role 自身确定并写入 manifest。

## remaining134 阶段式调度入口

`paired_campaign_dispatch.py --campaign_role remaining134` 从当前 234-sample inventory 中严格
减去 committed mixed confirmation100 的全部 100 个 planned sample；不因旧实验有 2 个未完成
而重新纳入。该 role 不接受 `--samples`，固定 10 RT、seed42、14 个物理唯一 Key 和每 Key
4 个 worker。

每个 Key 在单一方法阶段内持续即时补位。dispatcher 先耗尽 134 个 HP worker，保存唯一
`method_phase_complete` 屏障后才创建 FR worker；FR 的每次 refill 均重新检查屏障。恢复时只补
当前阶段未提交项，已提交 HP/FR round trip 均不重新 POST。统一 preflight 仍只运行 dry-run，
不会跨越阶段或发送 API；manifest 会固定完整 134 scope、两个方法阶段和 268 个 worker
invocation 的计划身份。

参数形态为：

```bash
--campaign_role remaining134 --num_round_trips 10 --seed 42 \
  --slots_per_key 4 --key_labels KEY_01 KEY_02 ... KEY_14 \
  --notes <experiment-note>
```

## 不能省略或混同的内容

- Key probe：真实 API，仍按既有流程独立执行；零 API receipt 不声称 Key 存活。
- evaluator runtime 通过：只证明当前初始状态可执行，不证明 evaluator 有足够区分度，
  也不证明 campaign 会完成。
- 计划审阅、污染边界、最终命令与预算复核：仍由实验计划和人工 GO/NO-GO 承担。
- 正式恢复：已提交 RT 不重发；使用同一 dispatcher 的 resume 检查。输入指纹未变时可
  复用零 API 回归和 evaluator，但本次 resume dry-run 与 Key probe 仍要按实际恢复命令核对。
